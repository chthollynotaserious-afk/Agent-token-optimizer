### 2. `178` 次（实测 `180` 次）唤醒为何产生这么多请求？
- 模型本身 **0 次网络重发 (`retry=0`)、0 次无工具连续调用 (`consecutive=0`)**。真正把 1 次唤醒放大到平均 `8.60–8.97` 次（极值 **`47–57` 次**）的原因是 **串行工具循环**：
  - **Stage 拆解**（`Bridge London Nov 11`）：`initial` 首跳仅 **`193` 次 (`12.5%`)**，`tool-continuation` 工具续跳高达 **`1,350` 次 (`87.5%`)**。
  - **协议控制步过度拆分**（`1,886` 次工具调用中过半为控制动作）：`qq_wait_for_messages` **`489` 次**（每次休眠回来重算一遍 144k 上下文）、`qq_send_message` **`434` 次**（多气泡按条调工具）、`qq_close_conversation` (`95`)、`qq_set_wake_config` (`64`)、`qq_mark_read` (`16`)。
  - **无收益空转**：`196` 轮中有 `66` 轮 **0 次成功出站（耗资 `¥3.080`）**，其中仅 `proactiveCheck` 闲群巡检就占 `26` 轮空转（`¥1.558`）。
  - **死工具诱发报错步**：`mcp__onebot-min__*` 已挂载却被权限禁止，实测诱发误调用并触发 180k 上下文的错误处理步。

### 3. 哪些调用可以安全合并或取消？
1. **直接取消**：下线冗杂死工具 `mcp-onebot-min` (`19` 工具 / `2,276` tok)；屏蔽冷会话（`idle > 30m`）纯随机 `proactiveCheck` 无效重唤醒（先跑纯本地评分门控）；把 `slang-learner` (`66` 轮/`88k` 无重置会话) 改为无状态单轮隔离或按批合并。
2. **安全合并**：允许 `qq_send_message` 单次传数组发多气泡（由 Bridge 异步延迟分条发出，保持拟人节奏不减）；将 `qq_mark_read(throughSeq)` 与 `qq_close_conversation` / `qq_set_wake_config` 折叠进末尾动作参数；取消潜水前强制调用 `qq_wait_for_messages(300s)` 的额外 LLM 回合。
3. **停止循环 Compaction**：通过定期干净轮转会话，把日均 `14` 次隐性高价 `compaction/summary`（`85.2%` 未命中！）降为近 `0`。

### 4. `141,994` Token 的平均输入主要由什么构成？
（`London Nov 11` 均值 **`144,013`**，中位 `149,693`，P90 `203,488`，极值 `232,683`）
1. **历史会话长期积累（最大头，约 `105k–125k` / `~75%–80%`）**：`qq-chat-v2` 无定期新建会话机制，`session-5d06` 跑到 Turn 92，`thresholdRatio: 0.22` (~`231k`) 叠加 `retainRatio: 0.06` 导致每次 Compaction 仅释放 `~46k` 空间、压缩后仍停在 **`140k–160k`** 巨型底盘，每 3–7 轮反复撞线。
2. **每次唤醒重复把 `13.5K–16.5K` 字符规则写进 `user/message` 历史**：`buildWakePromptV2` 每轮重复拼入 `role` (`4,807` 字)、`bili.briefBlock` (`1,089` 字)、`sticker` 策略 (`1,126` 字) 及十余条操作说明（约 `3,000` 字），占累计 `user/message` 体积 (`1.69MB` in `owner_5d06`) 的绝对主体。
3. **124 个全局工具 Schema（固定底盘约 `~26,700` Token / `~18%–20%`）**：`80,122` 字符由 9 个 MCP + 2 个内置工具组成，连无文件权限的群聊和 `slang` 也全量携带。
4. **System Prompt（约 `4,500–5,500` Token / `~3%–4%`）** 与 **Memory/本次快照（动态仅约 `~1,500–3,000` Token / `<2%`）**。

### 5. 当前 KV Cache 是否已经接近合理水平？
**远不合理。`96.46%` 表面高命中掩盖了真正的利润黑洞：**
- DeepSeek 未命中单价是命中的 **`50×`**（空闲 `¥1.00/M` vs `¥0.02/M`，高峰 `¥2.00/M` vs `¥0.04/M`）。
- 实测 **`3.54%` 的 Cache Miss 贡献了全天 Ledger 费用的 `53.4%` (`¥9.0868 / ¥17.0191`)**；而 42.7% 的费用来自仅占 12.5% 调用次数的 `initial` 首跳（均值高达 `26k` 未命中，空闲 `>30m` 首跳高达 `40.3k` 未命中）。
- 实证揭示 **三次不到 70 秒的间隔却打穿 `130k–197k` 全前缀缓存**：根源在于 **`compaction/summary` 改写历史** 与 **MCP 重连触发 `request/header` (`124 -> 63 -> 124`) / `developer/message (tool-addition)` / 新 `system/message`**。

### 9. 每项优化有哪些功能回归风险？
- 会话轮转可能丢失超过 30 轮前、未写入记忆卡的琐碎临场细节（通过自动附带高密度交接摘要 + 强制召回记忆卡缓解）；

- 取消强制 `300s` 沉睡等待会降低多句慢打场景的等待命中率（以 Bridge 短防抖合批替代）；
- 下调 `reasoningEffort` 须防止多人群聊指代判断变弱及 DNR 去 AI 味回归（保留主人命令/复杂推理高档，先从闲聊与 `slang` 灰度）。
